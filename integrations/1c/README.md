# Коннектор CODE QR PRO для 1С

Исследование и заготовка коннектора без установленной 1С.

## Что можно сделать без 1С

- HTTP/JSON-контракт API;
- общий модуль BSL для HTTP-запросов, JSON и статусов;
- пример модуля формы/команды;
- сопоставление документов 1С с полями API;
- примеры запросов curl/JSON для проверки API;
- инструкцию по сборке расширения `.cfe` в Конфигураторе.

Нельзя без 1С собрать бинарные `.epf`/`.cfe` и прогнать на реальной базе. Исходники ниже предназначены для вставки в расширение и проверки на тестовой копии.

## Целевые конфигурации

| Конфигурация | Приоритет | Комментарий |
|---|---|---|
| 1С:УТ 11.5 | 1 | опт, большинство B2B-сценариев |
| 1С:УНФ 3.0 | 2 | небольшой бизнес |
| 1С:Розница 3.0 | 3 | розница/кассы |
| 1С:ERP 2.5 | 4 | крупные компании, сложнее |

Требования: платформа 8.3.24+ (проверять на конкретном релизе), конфигурация ПРОФ, тестовая копия, модуль маркировки/интеграция с ЧЗ.

## Архитектура

1. Пользователь открывает документ 1С (заказ кодов, маркировка, ввод в оборот).
2. Команда расширения собирает полные коды и параметры печати.
3. `CodeQRProClient` вызывает `POST /api/v1/generate`.
4. 1С опрашивает `GET /api/v1/jobs/{id}` до `done`/`error`.
5. При необходимости скачивает архив/PDF или отправляет на Print Bridge.
6. Ошибки по строкам показываются в форме 1С.

## Сборка расширения

1. В Конфигураторе: Файл → Новый → Расширение конфигурации.
2. Добавить общий модуль `CodeQRProClient` (серверный, вызов сервера).
3. Вставить `CodeQRProClient.bsl`.
4. Создать форму команды/обработки и вставить `CodeQRProCommand.bsl`.
5. Добавить константу или безопасное хранилище для API-ключа.
6. Собрать `.cfe`, установить на тестовую базу.
7. Проверить на тестовом API-ключе и тестовом документе.

## API

Базовый URL: `https://code-qr.stockcity.ru`.

Заголовки:

```
X-API-Key: <ключ>
Content-Type: application/json; charset=utf-8
Accept: application/json
```

Создание задания:

```http
POST /api/v1/generate
```

```json
{
  "name": "УТ-000123",
  "mode": "cz",
  "format": "png",
  "rows": [
    { "data": "0104600000000015215Serial..." }
  ]
}
```

Статус:

```http
GET /api/v1/jobs/{id}
```

Проверка ключа и лимитов:

```http
GET /api/v1/me
```

Полные коды передавать целиком, включая криптохвост. Краткие коды (только GTIN/серийник) не подходят для проверки статуса.

## Ошибки

- `401` — неверный/отозванный API-ключ;
- `403` — API недоступен на тарифе или аккаунт заблокирован;
- `402` — лимит операций/проверок/экспорта/API;
- `400` — неверные rows/JSON/GTIN;
- `429` — слишком много запросов.

## Безопасность

- API-ключ хранить в константе/безопасном хранилище, не в тексте формы и не в репозитории;
- только HTTPS;
- не писать ключ в журнал регистрации;
- при утечке отозвать ключ в разделе «API» и создать новый;
- для тестов использовать отдельный ключ.
