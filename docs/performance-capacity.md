# Производительность и ёмкость CODE QR PRO

Дата измерений: 22.11.2026. Сервер: 4 vCPU, 4 ГБ RAM, Ubuntu 24.04, Node.js 20.20.2, SQLite (WAL), nginx 1.24.

## Что уже сделано

- HTTP/2 включён на nginx; gzip для HTML/JS/CSS/JSON/XML/SVG.
- Статика `/assets/*` отдаётся напрямую nginx с `Cache-Control: immutable`, минуя Node.
- Публичный HTML кэшируется в Node на 60 секунд (`stale-while-revalidate=300`), canonical/SEO-head не пересобирается на каждый запрос.
- Карточки товаров: параллельно до 6 и одна карточка на GTIN вместо запроса на каждый КИЗ.
- Тяжёлые штрихкоды — в пуле worker threads (до 4), фоновые PDF — не более 2 одновременно.

## Нагрузочный тест (главная страница, внешний клиент)

| Параллельных клиентов | RPS | p50 | p95 | p99 | ошибки |
|---:|---:|---:|---:|---:|---:|
| 10 | 300–417 | 10–17 мс | 22–37 мс | 233–240 мс | 0* |
| 30 | 570–584 | 46–49 мс | 82–87 мс | 103–268 мс | 0 |
| 60 | 748–900 | 65–75 мс | 92–131 мс | 145–294 мс | 0 |
| 100 | 796–852 | 112–120 мс | 187–191 мс | 246–291 мс | 0 |

\* один транзиентный сетевой сбой на клиенте, не ответ сервера.

Замеры сделаны двумя прогонами; цифры указаны диапазоном. До кэширования HTML и выноса статики в nginx было ~525 RPS при 60 клиентах и p95 177 мс.

## Оценка одновременных пользователей

Цифры ниже — про **активных пользователей**, а не про число открытых вкладок. Реальная нагрузка зависит от того, что именно делает пользователь.

| Сценарий | Ориентир без видимых задержек |
|---|---|
| Публичные страницы (главная, тарифы, статьи, FAQ) | ~500–1000 активных посетителей одновременно; синтетически сервер держит ~900 запросов/с |
| Кабинет: просмотр истории, баланса, обычные API-запросы | ~200–400 активных пользователей |
| Проверки кодов/карточки товара с внешними API | ~30–80 одновременных активных действий; ограничение — внешние API и лимиты проверок |
| Генерация PDF/этикеток | 2 фоновых PDF одновременно + 4 потока штрихкодов; при массовых очередях пользователи будут ждать |
| AI-помощник | ограничен бесплатным пулом Kilo/DeepSeek; при недоступности пула — fallback на платный backend |

Это не жёсткий предел «пользователей в системе», а предел одновременной активности. При текущем размере БД (1,3 МБ) и памяти Node (~118 МБ / 2,7 ГБ свободно) узкое место — не база и не RAM, а один процесс Node, внешние API и генерация PDF.

## Что оптимизировать дальше

1. **Nginx-микрокэш публичных страниц** на 10–30 секунд — снимет с Node повторные запросы роботов и посетителей. Сейчас кэш только внутри Node.
2. **Два процесса Node** (cluster/PM2) для HTTP: 4 vCPU сейчас использует в основном одно ядро. Фоновые задачи и планировщики должны остаться только в primary-процессе.
3. **Очередь тяжёлых PDF**: не запускать больше 2 сборок, отдавать клиенту задачу и прогресс; ограничение на пользователя, чтобы один пакет не занимал воркеры.
4. **Brotli** (если модуль есть в nginx) и `proxy_cache` для `/api/public/articles`.
5. **Мониторинг**: p95/p99, event loop lag, CPU, RSS, очередь PDF, ошибки внешних API. Сейчас есть slow_request-предупреждения, но нет алертов по p95 и загрузке.
6. **SQLite**: `PRAGMA optimize` по расписанию, индексы под `site_visits`/`sessions`/`orders`; при росте записей >50/с или БД >1–2 ГБ — переход на PostgreSQL.
7. **Внешние API**: circuit breaker и короткие таймауты, кэш карточек/статусов, чтобы зависший внешний сервис не занимал параллельные слоты.

## Практический вывод

Для текущего трафика запаса достаточно. Публичный сайт выдерживает сотни запросов в секунду; кабинет и проверки — десятки одновременных активных действий. Если ожидается рост до тысяч одновременно работающих пользователей или массовая генерация этикеток, в первую очередь нужны второй Node-процесс, nginx-кэш и отдельная очередь PDF.
