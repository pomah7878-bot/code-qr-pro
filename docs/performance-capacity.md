# Производительность и ёмкость CODE QR PRO

Дата измерений: 22.11.2026. Сервер: 4 vCPU, 4 ГБ RAM, Ubuntu 24.04, Node.js 20.20.2, SQLite (WAL), nginx 1.24.

## Текущая схема

- **3 HTTP-воркера Node.js** в cluster-режиме; primary только супервизор.
- Фоновые задачи, планировщики, mail queue и Telegram-бот запускаются **только в worker 0**.
- SQLite: WAL, `busy_timeout=5000`, `synchronous=NORMAL`, общая БД у всех воркеров.
- PDF: 1 фоновая сборка на воркер (всего до 3); штрихкоды — 2 worker threads на воркер.
- Nginx: HTTP/2, gzip для HTML/JS/CSS/JSON/XML/SVG, статика `/assets/*` отдаётся напрямую с `immutable`.
- Публичный HTML кэшируется в Node на 60 секунд, отдаётся с `stale-while-revalidate=300`.
- Карточки товаров: до 6 параллельно и одна карточка на GTIN.
- Память: ~400 МБ на 3 воркера + ~50 МБ primary; свободно ~2,6 ГБ.

## Оценка одновременных пользователей

| Сценарий | Ориентир |
|---|---|
| Публичные страницы (главная, тарифы, статьи, FAQ) | **~2000–3000 активных посетителей** при обычном просмотре; сервер держит 2,5–3 тыс. запросов/с локально |
| Кабинет: история, баланс, обычные API-запросы | **~500–1000 активных пользователей** |
| Проверки кодов/карточки с внешними API | **~30–80 одновременных активных действий**; ограничение — внешние API и лимиты проверок |
| Генерация PDF/этикеток | до 3 фоновых сборок одновременно + 6 потоков штрихкодов; при массовых очередях пользователи ждут |
| AI-помощник | ограничен бесплатным пулом Kilo/DeepSeek; есть fallback на платный backend |

Это не «жёсткий лимит пользователей в системе», а оценка одновременной активности. При росте дальше узкие места — внешние API, генерация PDF и единственная SQLite-БД.

## Что сделано для нагрузки

- cluster на 3 воркера — используются все 4 vCPU, а не одно ядро;
- фоновые задачи не дублируются между воркерами;
- HTTP/2 и сжатие;
- статика через nginx;
- кэш публичного HTML;
- параллельная загрузка карточек и дедупликация по GTIN;
- ограничение PDF-сборок;
- `busy_timeout` для SQLite.

## Следующие шаги

1. nginx-микрокэш публичных страниц на 10–30 секунд — снимет с Node повторные запросы.
2. Мониторинг p95/p99, event loop lag, CPU, RSS и очереди PDF + алерты.
3. Общий rate-limit (Redis/БД) вместо трёх независимых in-memory лимитов в воркерах.
4. Очередь тяжёлых PDF с ограничением на пользователя.
5. Brotli и `proxy_cache` для `/api/public/articles`.
6. При росте записей/БД — PostgreSQL; сейчас БД 1,3 МБ и не является узким местом.

## Вывод

Сервис подготовлен к заметно большей одновременной нагрузке: публичная часть держит тысячи активных посетителей, кабинет — сотни. Для массовой генерации этикеток и дальнейшего роста нужны очередь PDF, nginx-кэш и общий rate-limit.
